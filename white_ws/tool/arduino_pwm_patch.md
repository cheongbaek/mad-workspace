# 아두이노 패치 — PWM 클램프 205 → 255

현재 사용 중인 스케치(`PS2 우선권 + 통신 워치독 페일세이프판`) 기준입니다.

---

## 왜 2.2 m/s 에 PWM 252 가 필요한가

**PWM 은 속도 명령이 아니라 속도PID 의 출력**입니다. 흐름은 이렇습니다:

```
ROS(driving.py)  "2.2 m/s"
      ↓  motor.py:  tick = v · ENC_DT · TICKS_PER_REV / WHEEL_CIRC
Arduino 수신      "C,8,steer"   ← 2.2 m/s = 7.78 tick/10ms
      ↓  Velo_PID_Control():  velo_val(8) 을 맞추려 PWM 을 올림
모터              PWM 출력
```

실측 기준점은 **PWM 205 포화에서 평지 1.79 m/s** 입니다. DC 모터 속도는 인가 듀티에
대략 비례하므로:

| 목표 속도 | 필요 PWM |
|---|---|
| 1.79 m/s | 205 (현재 클램프) |
| 2.00 m/s | 229 |
| **2.20 m/s** | **252** |
| 2.23 m/s | 255 (물리 최대) |

즉 2.2 m/s 를 유지하려면 PID 출력이 252 까지 올라가야 하는데, **205 에서 잘리고 있었습니다.**
그래서 아무리 명령해도 1.79 m/s 를 못 넘었습니다.

**255 로 풀었을 때 도달 가능:** 평지 2.23 / 오르막 1.79 / 내리막 2.56 m/s

> ⚠️ 목표 2.2 는 평지 상한 2.23 의 **99%** 입니다. 헤드룸이 거의 없어 평지에선 겨우 도달하고
> **오르막에선 여전히 포화**가 남습니다. 울컥거림이 거슬리면 `max_speed_ms` 를 2.0 으로
> 내리는 게 안전합니다 (`ros2 param set /driving_node max_speed_ms 2.0`, 재빌드 불필요).

## 패치 A — 속도 PWM 클램프 해제 (요청 사항)

### A-1. 상수 추가

`velo_Kd` 정의 아래에 한 줄:

```c
#define velo_Kp  12
#define velo_Ki  0.25
#define velo_Kd  15

#define VELO_PWM_MAX  255      // ← 추가. 구 205(=255의 80%). 되돌리려면 205
```

### A-2. `Velo_PID_Control()` 안 `205` 네 곳 교체

```c
    PWM = (int)(velo_Kp * Error + velo_Ki * Sum_Error + velo_Kd * d_Error);
    if (PWM > VELO_PWM_MAX) {
      PWM = VELO_PWM_MAX;
      Sum_Error -= Error * dt_ratio;
    }
    if (PWM < -VELO_PWM_MAX) {
      PWM = -VELO_PWM_MAX;
      Sum_Error -= Error * dt_ratio;
    }
```

> 전체 파일에서 `205` 는 이 네 곳뿐입니다(조향 쪽은 `PWM_LIMIT = 255` 로 별개).

### ⚠️ 올리기 전 확인

**205/255 = 정확히 80%** 입니다. 배터리 24V + 모터 정격 19V 라면 `19/24 ≈ 0.79` 로 딱
맞아떨어집니다. 이 경우 255 는 정격 초과입니다. 모터·드라이버 정격을 확인하시고,
불확실하면 **229(=2.0 m/s 상당)** 에서 멈추세요.

올린 뒤 첫 주행에서는 **모터·드라이버를 손으로 만져 발열을 확인**하시길 권합니다.

## 패치 B — 조향 데드밴드 (오실레이션의 진짜 원인) · 권장

이번 로스백 분석에서 **직진 오실레이션의 발생지가 ROS 가 아니라 이 조향 PID** 로 확인됐습니다.

```
조향 명령 → 실제 요레이트   lag 1.05s,  r = +0.646
회귀 기울기 0.489        →  명령한 조향의 49% 만 실현
조향 명령 변화의 97.4% 가 1.0° 미만  ← 데드밴드 이하
```

현재 코드:

```c
void Steer_PID_Control(float dt_s) {
  error_s = (double)Steering_Angle - (double)Steer_Angle_Measure;
  if (fabs(error_s) <= STEER_DEADBAND) {          // 1.0°
    steer_motor_control(0);
    error_i_s = 0.0;                              // ★ 문제: 적분 통째로 버림
    pwm_prev_s = 0;
    error_old_s = error_s;
    return;
  }
```

**리밋사이클이 생기는 과정**

1. ROS 가 조향을 평균 0.28° 씩 미세 조정 → 97% 가 데드밴드 안 → 모터가 안 움직임
2. 오차가 1.0° 를 넘는 순간에만 모터 작동
3. 움직이기 시작하면 `Ki_s=1.8` 적분이 **0 부터 다시** 쌓임 → 응답 지연
4. 목표에 근접해 오차가 1.0° 아래로 들어가면 **즉시 정지 + 적분 리셋**
5. 다시 벗어날 때까지 방치 → 1번으로

크기도 맞습니다 — 조향 1.0° 오차는 전방주시 통과시간 동안 횡오차 **0.14m**(1.22 m/s)를
만드는데, 실측 |CTE| 0.100m 와 같은 규모입니다. **데드밴드가 CTE 하한을 정하고 있습니다.**

### B-1. 적분 리셋 제거 (위험 없음, 먼저 이것만)

```c
  if (fabs(error_s) <= STEER_DEADBAND) {
    steer_motor_control(0);
    // error_i_s = 0.0;          // ← 삭제: 데드밴드 안이라고 적분을 버리면
    //                           //    정상상태 오차를 잡으려 쌓은 값이 매번 사라져
    //                           //    빠져나오는 순간 응답이 늦어진다(리밋사이클 원인).
    pwm_prev_s = 0;
    error_old_s = error_s;
    return;
  }
```

### B-2. 데드밴드 축소 (B-1 로 부족하면)

```c
const float STEER_DEADBAND = 0.4;   // 구 1.0
```

> 너무 줄이면 모터가 상시 미세진동(치터링)할 수 있습니다. 1.0 → 0.4 정도부터 시도하고,
> 정지 상태에서 조향 모터가 계속 떠는지 확인하세요.

### ⚠️ 속도를 올리면 이 문제가 커집니다

| 속도 | 데드밴드 1.0° 가 만드는 횡오차 |
|---|---|
| 1.22 m/s | 0.140 m |
| **2.20 m/s** | **0.245 m** |

전방주시 통과시간이 짧아지는 것보다 요레이트 오차가 커지는 효과가 더 크기 때문입니다.
**2.2 m/s 로 올리실 거면 패치 B 를 같이 하시는 걸 권합니다.**

## 패치 C — d_val 절삭 버그 (★ 최우선 · DR 실패의 근본 원인)

### 문제

```c
float scale = (float)VELO_PID_PERIOD_US / (float)elapsed_us;
d_val = (signed long)((float)d_val_raw * scale);   // ← C 캐스팅 = 0쪽으로 절삭
```

`loop()` 가 빨라서 `elapsed_us` 는 보통 10000~11000us → `scale ≈ 0.91~1.00`.
따라서 곱셈 결과가 소수가 되는데, **C 의 정수 캐스팅은 항상 내림**입니다.

| d_val_raw | scale | 정확값 | d_val | 손실 |
|---|---|---|---|---|
| 6 | 0.95 | 5.70 | **5** | 0.70 |
| 3 | 0.95 | 2.85 | **2** | 0.85 |
| 10 | 0.95 | 9.50 | **9** | 0.50 |

이 손실이 **매 10ms 누적**됩니다. ROS 는 `d_val` 을 적분해 거리를 얻으므로
**주행거리가 계통적으로 짧아지고, 저속일수록 손실 비율이 커집니다.**

### 실측 검증 (로스백 3개, 10초 창 14개)

| 속도 | 실틱 | 절삭효과 예측 | 실측 GPS/엔코더 |
|---|---|---|---|
| 0.51 m/s | 1.80 | 1.383 | 1.427 |
| 1.21 m/s | 4.28 | 1.132 | 1.227 |
| 2.08 m/s | 7.36 | 1.073 | 1.103 |

**오차 분해**: `실측 = 절삭효과 × 일정배율`
잔여 배율 평균 **1.070**, 속도와의 상관 **r=+0.017**(= 속도 무관).

→ **두 원인이 겹쳐 있었습니다**
- **① d_val 절삭** — 속도 의존 (저속 28% ~ 고속 6% 과소)
- **② 스케일 상수** — 일정 7% 과소

### 수정

```c
    // 반올림으로 바꿔 계통 편향 제거 (평균 오차 −0.5틱 → 0)
    d_val = (signed long)lroundf((float)d_val_raw * scale);
```

> `math.h` 는 이미 include 되어 있습니다.

**더 정확히 하려면**(선택) 잔차를 다음 주기로 이월:

```c
static float d_resid = 0.0f;
float exact = (float)d_val_raw * scale + d_resid;
d_val  = (signed long)lroundf(exact);
d_resid = exact - (float)d_val;     // 버린 소수를 다음에 더해준다
```

이러면 장기 적산 오차가 0 으로 수렴합니다(DR 에 유리).

### 순서가 중요합니다

**패치 C 를 먼저 적용하고 다시 측정해야** 남은 스케일 오차(②, 약 7%)를 정확히 잡을 수 있습니다.
지금 `WHEEL_CIRCUMFERENCE` 만 건드리면 저속·고속 중 한쪽만 맞고 다른 쪽이 틀어집니다.

C 적용 후 재측정해서 비율이 **속도와 무관한 일정값**으로 나오면, 그 값을 그대로
`WHEEL_CIRCUMFERENCE`(driving.py·motor.py 양쪽)에 곱하면 됩니다.

| 항목 | 값 |
|---|---|

| `min_speed_ms` | 0.80 (자동 산출) |
| CTE 회복 캡 | 1.73 / 1.34 / 0.94 |
| 조향 반응 캡 | 1.81 / 1.41 / 1.02 |
| 접근 진입속도 | 2.04 |

**LFD·PID 테이블은 수정하지 않았습니다.** 두 표 모두 **절대속도 인덱스**라 상한을 바꿔도
재스케일 대상이 아니고, 2.2 행은 원래 이 속도용으로 튜닝된 값이기 때문입니다:

| v | LFD | ω_n | Kp | Ki | Kd |
|---|---|---|---|---|---|
| 1.0 | 2.3 | 0.61 | 1.7 | 0.12 | 0.11 |
| 1.4 | 2.5 | 0.79 | 1.9 | 0.14 | 0.14 |
| 1.8 | 2.8 | 0.91 | 2.1 | 0.16 | 0.17 |
| **2.2** | **3.2** | **0.97** | **2.3** | **0.20** | **0.21** |

(2.5 / 2.8 행은 상한 초과로 미사용)

앞서 LFD 를 올려봤다가 **코너 CTE 가 +106%** 되어 철회한 이력이 있습니다. 지금 진동의
원인이 아두이노 데드밴드로 밝혀졌으므로, **표를 건드리기 전에 패치 B 로 실측을 다시 잡는
것이 순서**입니다. 그래도 남으면 그때 조정하시죠.

## 적용 순서

1. **패치 C** (d_val 반올림) — ★최우선. DR 오차·속도 부정확의 근본 원인
2. **패치 B-1** (적분 리셋 제거) — 위험 없음. 이것만으로 진동이 줄면 B-2 불필요
3. **패치 A** (PWM 255) — 모터 정격 확인 후
4. 주행 → 로스백. 확인할 것:
   - 속도 달성률(목표 2.2 대비)과 PWM 포화 여부
   - 직진 조향 std (직전 2.81°) 와 조향반전/분
   - 모터·드라이버 발열
   - **GPS/엔코더 비율이 속도와 무관한 일정값이 됐는지** (패치 C 검증)
5. 결과 보고 `WHEEL_CIRCUMFERENCE` 보정, `max_speed_ms` 2.0 하향, 패치 B-2 여부 결정
